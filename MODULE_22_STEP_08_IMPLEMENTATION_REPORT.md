## PREFLIGHT FINDINGS, RULES & CORRECTION GOVERNANCE

---

### 1. Executive Summary
Module 22 Step 08 establishes canonical **Preflight Findings, Rules & Correction Governance** for Sucharu Pro. Findings discovered during technical preflight execution now follow a strict, auditable lifecycle:
`OPEN → ACKNOWLEDGED → CORRECTION_REQUIRED → CORRECTION_SUBMITTED → REVALIDATION_REQUIRED → RESOLVED / ACCEPTED / WAIVED`.

Key Invariants Maintained:
- **Correction Submitted ≠ Correction Validated**: Submitting artwork or metadata correction transitions the finding to `REVALIDATION_REQUIRED`, never automatically to `RESOLVED`.
- **Evidence-Based Resolution**: Finding resolution requires running a new preflight revalidation run via `PreflightEngine`. If the technical defect persists, the finding remains `CORRECTION_REQUIRED`.
- **Audit & Evidence Preservation**: Historical runs, findings, and correction records are immutable and preserved for compliance.
- **Strict Role & Tenant Governance**: Cross-tenant actions are rejected via tenant context and PostgreSQL Row Level Security (RLS). Manager justification is enforced for waivers.

### 4. Existing Finding Architecture
Findings are generated by `PreflightEngine` executing rules from `PreflightRuleRegistry`. Each `PreflightFinding` contains:
- `findingId`: Unique canonical key.
- `tenantId`: Multi-tenant isolation context.
- `preflightRunId`: Linked preflight run execution.
- `ruleCode`, `category`, `severity`: Rule classification (`INFO`, `WARNING`, `ERROR`).
- `message`, `expectedValue`, `actualValue`, `locationContext`: Detailed evidence.
- `status`: `PreflightFindingStatus` lifecycle enum.

---

### 5. Finding Lifecycle
```
                   [ FINDING DETECTED ]
                            │
                            ▼
                         ( OPEN )
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
       ( ACKNOWLEDGED )          ( CORRECTION_REQUIRED )
              │                           │
              └─────────────┬─────────────┘
                            ▼
                  [ CORRECTION SUBMITTED ]
                            │
                            ▼
                ( REVALIDATION_REQUIRED )
                            │
               [ PREFLIGHT RE-RUN EXECUTED ]
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
     Defect Cleared                Defect Persists
              │                           │
              ▼                           ▼
         ( RESOLVED )            ( CORRECTION_REQUIRED )
```
Alternatively, an authorized manager may apply a `WAIVED` terminal state with mandatory written justification.

---

### 6. Correction Governance
Submitting a correction creates a `PreflightFindingCorrection` entity containing:
- `correctionId`, `tenantId`, `findingId`, `preflightRunId`
- `correctionType`: (`FILE_REPLACEMENT`, `METADATA_CORRECTION`, `SPECIFICATION_CORRECTION`, etc.)
- `description`: Written explanation of changes made.
- `artworkVersionId`: Optional updated artwork version reference.
- `submittedBy`, `submittedAt`.

Guard: Submitting a correction transitions the finding to `REVALIDATION_REQUIRED`—it does NOT resolve the finding.

---

### 7. Revalidation Flow
Revalidation executes a new `PreflightRun` using `PreflightEngine` and the updated `PreflightExecutionContext`.
- If the rule code is no longer failing: Finding transitions to `RESOLVED` with `resolvedBy`, `resolvedAt`, and `revalidationRunId`.
- If the rule code is still failing: Finding returns to `CORRECTION_REQUIRED` with `revalidationRunId` recorded.

---

### 8. Finding Resolution Logic
Finding resolution is strictly evidence-driven through revalidation. Manual resolution without revalidation or manager waiver is prohibited by `PreflightFindingValidator`.

---

### 9. Waiver/Acceptance Governance
Waivers require `ADMIN` or `MANAGER` role capability.
- `waiveFinding` requires `waiverReason` and `waivedBy`.
- Transitions finding to terminal `WAIVED` state.
- Terminal states cannot be re-opened or re-edited.

---

### 10. Rule Governance
Preflight rules expose rule code, name, category, severity, description, and correction guidance. The registry (`PreflightRuleRegistry`) evaluates active rules dynamically against the execution context.

---

### 11. Authorization
Backend endpoints enforce role capabilities via `BackendAuthorizationPolicy`:
- `acknowledgeFinding`, `submitFindingCorrection`, `revalidateFinding`: `ADMIN`, `MANAGER`, `STAFF`.
- `waiveFinding`: `ADMIN`, `MANAGER` ONLY (`STAFF` receives `403 Forbidden`).
- `listCorrectionsForFinding`, `listPreflightFindings`: `ADMIN`, `MANAGER`, `STAFF`, `CUSTOMER`.

---

### 12. Tenant Isolation
Tenant boundaries are strictly enforced:
- Data queries filter by `tenant_id = principal.projectId`.
- Cross-tenant requests return `DomainResult.Error("Preflight finding '...' not found")` or `404/403`.

---

### 13. IDOR Protection
IDOR checks verify that resource IDs belong to the authenticated tenant context before performing update/waiver operations.

---
